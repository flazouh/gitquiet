A repository's own page — three ways to arrange it

Real data from flowline-labs/flowline, read off the live page: 28 entries at the root, 2,488 commits on main, 25 tags, a 35 KB README. Every one of these three costs no extra requests. GitHub already puts the file list, the README, the branch, the counts, the website and the topics into the page as JSON, and all three read the same payload.

A. The README firstrecommended

The reader came to find out what this is. GitHub puts 28 rows of build configuration between them and the sentence that says so. This turns that around: a strip of facts, the README, and the files underneath for when the question is a file.

The file list on its own — the part I asked badly

Three ways to draw the same 28 entries. This is the only choice that costs a request, and it is the middle one.

Draw Looks like Costs
Plain (used in A and B) Name only, folders first, two columns. 28 entries in 14 rows. Nothing. It is in the page already.
With last commit (used in C) Name, then the message of the last commit that touched it, then how long ago. One column, 28 rows. One request to their tree-commit-info, and it is what makes GitHub's own tree arrive late.
Short The first eight entries and a "show the rest" control. Nothing. Fits more of the README on the screen.
